What the machine itself has noticed

The nightly discovery pass reads the accumulated record and may propose observations and sensors. Everything below was written by the machine and cites committed files; promotion to a standing sensor is a separate, reasoned commit.

The machine’s standing sensor measures nightly: 41 of 98 open alert episodes appear in a 2026 UN response plan (42%).

STANDING fts-country-coverage

For each OPEN ALERT_EPISODE future, whether at least one of its iso3 codes appears among the iso3 codes listed in the most recently preserved OCHA/FTS response-plan snapshot (foreknown/snapshots/<latest date>/fts-plans-2026.json, field data[].locations[].iso3). A purely mechanical membership check between two already-committed registers — no funding amount, adequacy, or need judgement is made or implied.

The check now runs on every nightly run and its value is committed: has_fts_plan_match per open alert episode, plus the aggregate match rate. First measured value, 2026-08-08: 37 of 100 open alert episodes (37%). The sensor stands because it measures, not because it has found anything.

IMPLEMENTED cold-start-overdue-drift

Splits the existing `overdue` signal (practice/src/practice/foreknown/futures.py, is_overdue) into two distinct kinds: cold_start_overdue (a future whose window.to already lay in the past on the very night it was first notarized — announced_at[:10] == first seen date and is_overdue true at NOTARIZED time) versus drift_overdue (a future that was NOT overdue when the observatory first saw it, and only became overdue on a later run while still OPEN, meaning it outlived the window it was announced with). Tonight's run.json shows 100/100 notarized futures already listed as overdue on their first night (foreknown/snapshots/2026-08-08/run.json: `notarized` and `overdue` are the same 100 ids) — entirely cold_start_overdue, since this is the observatory's first night and every future is by definition being seen for the first time. drift_overdue cannot exist yet and will only become measurable from the second run onward.

The proposal asks for promotion only after at least one drift_overdue case has been observed and its history inspected by hand. Tonight there are none and there cannot be: every future in the registry was notarized on the observatory's first night, so all 100 overdue flags are cold starts by construction. Building the split now and promoting it later keeps the two decisions apart — the code exists so the evidence can appear, and the evidence still has to appear.

PROPOSED attention-catchup-latency

For each nightly reaction run, the gap in days between the run's own date and `attention_day` (the newest committed day in foreknown/reaction/attention/), and whether the immediately-preceding day was retried and still failed with 'not published yet'. practice/src/practice/foreknown/reaction.py (run_reaction, lines 292-320) retries every missing day between the backfill horizon and yesterday on every run, not only the newest one, so a failed day is not lost — but if the notary consistently runs before GDELT's daily file for the prior day is published, the gap could sit at 2 days indefinitely rather than the 1-day lag the code's own comment expects ('GDELT publishes a day's file the following morning'). Across the two nights so far: 2026-08-08's reading shows attention_day=2026-08-07 with zero failures (that run never attempted 2026-08-08, since days_before() only generates days strictly before the run's own date); 2026-08-09's reading also shows attention_day=2026-08-07, this time after one attempt at 2026-08-08 that failed 'not published yet' (foreknown/reaction/readings/2026-08-09.json, failures). attention_days_committed has not grown past 60 in either recorded night.

PROPOSED forecast-kind-gap

Watches whether the observatory has notarized any kind==FORECAST future in the last N nights, given that the resolver's MATERIALIZED_AS_ALERT verdict and lead_time_hours measurement (practice/src/practice/foreknown/resolve.py, resolve_future, lines 96-121) can only ever fire against a FORECAST-kind future, and the only FORECAST-kind source configured is NHC (practice/src/practice/foreknown/sources.py, nhc_futures). Tonight's NHC snapshot (foreknown/snapshots/2026-08-08/nhc-current-storms.json, 24 bytes) returned activeStorms: [] — an honest quiet state per the source's own docstring, but the result is that foreknown/registry.json holds zero FORECAST-kind futures after the observatory's first night, so the lead-time measurement this project was built to eventually produce (docs/2026-08-09-foreknown-001-audit-und-entwurf.md, 'Was bewegte sich zwischen Warnung und Ereignis') has never had a case to run on.

The proposal asks for N=14 consecutive nights before it fires. This is night 1. Promoting it now would mean overriding the machine's own condition with a human's impatience, and the blind spot it watches cannot be measured faster than it fills.

PROPOSED primary-iso3-gap

For every GDACS-sourced future, whether the raw feed's top-level singular `properties.iso3` (the event's current/reporting-position country) is a member of the future's committed `iso3` array, which practice/src/practice/foreknown/sources.py (gdacs_futures, lines 48-50) builds only from `properties.affectedcountries`. obs-2026-08-09-1.json found six tropical-cyclone futures in both preserved GDACS snapshots (2026-08-08 and 2026-08-09) where the top-level iso3 is absent from affectedcountries and therefore absent from the future's iso3 array, even though the same country is named in the future's own `where` text. A purely mechanical field-membership check against already-preserved raw snapshot bytes — no judgement about which country is 'really' affected.

PROPOSED registry-stall

Whether any register (foreknown/snapshots, foreknown/reaction/snapshots, darkocean/snapshots) has committed a manifest.json dated the immediately-preceding UTC day. Distinct from every source-outage signal already recorded (GDACS/NHC/FTS failures in run.json, the DMA outage in darkocean readings, the reaction axis's 'not published yet' retries) because those all presuppose the notary job reached the point of writing a manifest and committing it -- this sensor instead asks whether the job got that far at all, which none of the existing per-source checks can see from inside a run that never committed. obs-2026-08-11-1 found exactly this blind spot: verify.py's check_anchors (added 2026-08-09) makes every sentinel and darkocean run fail at the pre-commit verify step, so no failure was ever recorded as a source outage, a resolver failure, or an autonomy/log.jsonl entry of any kind -- the only trace was the absence of new snapshot directories and two 'failure' conclusions visible in GitHub's own Actions history, neither of which this repository's committed records surface on their own.

Red-alert rate varies eightfold across hazard types within the same feed and scale

Earthquake episode windows are structurally instantaneous, not short

Every one of the 30 earthquake futures in foreknown/registry.json has window.from == window.to (30/30). No other hazard behaves this way: flood has 2/24 instant windows, wildfire 1/20, tropical cyclone 0/20, drought 0/6. This is not a record of unusually brief earthquakes — it is GDACS reporting earthquake onset as a single timestamp rather than an episode span, while flood, drought and most wildfire/cyclone records carry a genuine multi-day or multi-month window. The resolver (practice/src/practice/foreknown/resolve.py, function resolve_future, lines 86-94) computes `episode_days` from window.from/to for every ALERT_EPISODE kind, earthquakes included. Once earthquake futures start closing, their episode_days will read as 0.0 for all 30 — a source-schema artifact, not a measured duration.

GDACS's own primary country is dropped from six tropical-cyclone futures' iso3 lists — Vietnam never appears in the registry despite being named in five of them

GDACS's raw event feed carries two country fields per feature: a top-level singular `iso3` (the storm's current/reporting position, e.g. "MHL") and a list field `affectedcountries` (other countries in the episode's footprint). practice/src/practice/foreknown/sources.py (gdacs_futures, lines 48-50) builds the future's human-readable `where` text from a third field, `country` (free text naming every place GDACS mentions), but builds the machine-readable `iso3` array from `affectedcountries` alone — it never reads the top-level singular `iso3` field. In both preserved GDACS snapshots (2026-08-08 and 2026-08-09), six tropical-cyclone features carry a top-level `iso3` that is absent from their own `affectedcountries`, so the future's `where` text names one more country than its `iso3` array records: gdacs-tc-1001297 ("Marshall Islands, Japan, China" -> iso3 [CHN, JPN], missing MHL), gdacs-tc-1001281, gdacs-tc-1001219, gdacs-tc-1001214, gdacs-tc-1001199 (each "Viet Nam, ..." -> iso3 missing VNM), and gdacs-tc-1001270 ("Northern Mariana Islands, Guam" -> iso3 [GUM] only, missing MNP). The gap is stable, not a one-night glitch: identical for the same six event ids in both foreknown/snapshots/2026-08-08/gdacs.json and foreknown/snapshots/2026-08-09/gdacs.json, and it has held in foreknown/registry.json since the futures were first notarized on 2026-08-08. Across the full 100-future registry, Viet Nam is named in the `where` text of six tropical-cyclone futures (gdacs-tc-1001199, -1001214, -1001219, -1001229, -1001233, -1001281) and VNM appears in the `iso3` array of zero of them. The gap propagates downstream unlabeled: foreknown/reaction/readings/2026-08-09.json computes each future's `fips` list and GDELT attention-article count from the same `iso3` array (practice/src/practice/foreknown/reaction.py, build_reading, lines 191-202), so gdacs-tc-1001297's 24,742 attributed articles are counted only for China and Japan fips codes — Marshall Islands' news volume is never counted for that cyclone, and the same holds for Vietnam across its five entries. The FTS plan-match check (has_fts_plan_match, same lines) is computed from the identical incomplete iso3 array, so a funding plan naming Vietnam, the Marshall Islands or the Northern Mariana Islands could never register a match through these six futures even if one existed.

The anchor-coverage check added 2026-08-09 makes every sentinel and darkocean run fail by construction — the observatory has notarized no new night since 2026-08-09

verify.py's check_anchors (verify.py, lines 493-528) requires that every manifest matching the glob `*/**/snapshots/*/manifest.json` found ON DISK already appear in anchors/ledger.json (line 525-528: 'every register night must appear in the ledger, anchored or not'). sentinel.yml and darkocean.yml both run `python -m practice.foreknown.run` / `python -m practice.darkocean.run` (which write that run's own new manifest.json file to the working tree) and THEN run `python verify.py --repo-root .` in the same job, before the commit step (sentinel.yml 'Notarize announced futures' -> 'Verify provenance chain' -> 'Commit observation'; darkocean.yml 'Coverage-vs-Declaration reading' -> 'Verify provenance chain' -> 'Commit reading'). tools/anchor.py's own manifests() (tools/anchor.py, lines 76-81) globs the SAME pattern, but anchor.yml runs as a separate scheduled job (cron '20 6 * * *', after darkocean's '50 4 * * *' and sentinel's '45 5 * * *' per their own workflow comments) that checks out main FRESH and can only ever anchor a manifest that is already committed there.

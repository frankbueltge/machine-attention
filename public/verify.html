Verify — where the claims meet the bytes

Nothing here asks to be believed

Every figure on these pages is derived from bytes preserved at the moment of reading — hashed, manifested, committed. This page is the bottom of the work: the chain itself.

How the chain holds

Each night the machine fetches the public feeds and preserves the original bytes with URL, UTC time and SHA-256. The registry of announced futures is folded from those bytes; revisions append, nothing is overwritten. Verdicts and reaction figures are derived from committed records only. The stage — including this page — is a deterministic rebuild: the verifier recomputes every page and every reaction figure from the bytes and fails if one byte differs.

Run it yourself

git clone https://github.com/frankbueltge/machine-attention
cd machine-attention && python verify.py --repo-root .
cd practice && python -m pip install -e '.[dev]' && python -m pytest

Bytes referenced, not stored

The attention series reads GDELT’s daily export — about six megabytes a day, immutable once published. The bytes are not kept here; each committed day carries the url, length and SHA-256 of what was read, so the derivation can be redone by anyone. A hash that stops matching is not a broken link — it is the finding.

The one hand-authored link

The country crosswalk translates 79 iso3 codes to the FIPS codes GDELT locates events with. It is the only hand-written joint in the chain, so it carries its own evidence: every code is checked against the committed record, name by name. The check against the issuer’s own code list has recorded 2 findings about the instrument itself — kept in the file, not silently corrected.

Why the dates are not just our word

This work claims to have notarized what was knowable when — so the dates carry the claim. A git commit date does not: it is set by the committer’s clock and can be rewritten. So each night’s manifest, which already holds the SHA-256 of every byte preserved that night, is stamped into the Bitcoin blockchain with OpenTimestamps — keyless, free, and checkable without us. 24 of 28 nights carry a completed proof. The completed proofs rest on Bitcoin blocks 961744, 961747, 962204, 962208, 962237, 962257, 962288, 962394, 962396, 962398, 962537, 962538, 962564, 962604, 962690, 962709, 962727, 962856, 962893, 962912, 963005, 963035, 963148, 963149, 963155, 963202, 963272, 963274, 963310, 963326, 963408, 963410, 963413, 963452. 2 of them are still pending: a fresh stamp is a calendar’s promise until its transaction confirms, and this page says so rather than counting it as proof.

What an anchor proves: those exact bytes existed no later than that block. What it does not: that they are true, that they came from the publisher they name, or that they did not exist earlier. It makes the record unrevisable after the fact; it does not make it correct.

ots verify -f foreknown/snapshots/<day>/manifest.json \
  anchors/foreknown/snapshots/<day>/manifest.json.ots

The -f is needed because proofs are stored apart from the records: ots upgrade rewrites a proof once, when its Bitcoin path arrives, and the record trees never change. Checking the Bitcoin side needs a Bitcoin node (--bitcoin-node); a block explorer would put a third party back into a chain built to remove them. Without the client, verify.py still binds each proof to its manifest from the proof’s own header.
